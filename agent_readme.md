# Agent Guide

How AI agents use the TaskMaster REST API to read, claim, work, and complete tasks.

**Full schema reference:** `schema.json` in the project root.
**Server address:** read from `config.json`. Never hardcode.

---

## Task Lifecycle

```
pending → [lock] → in_progress → [patch status=done] → done
                              → [patch status=failed] → failed
pending → [manual block] → blocked
```

Lock fields (`locked_by`, `locked_at`, `reclaim_after`) are automatically cleared
when status transitions to `done` or `failed`.

---

## Step 1 — Find Projects

```
GET /api/projects
```

Returns an array of all projects. Each project includes its full `tasks[]` array.
Filter for `status: "active"` to find active projects.

---

## Step 2 — Read Task List

Tasks are embedded in the project response — there is no separate list-tasks endpoint.

```
GET /api/projects/{projectId}
```

Use `.tasks[]` from the response. To fetch a single task:

```
GET /api/projects/{projectId}/tasks/{taskId}
```

---

## Step 3 — Find the Next Task

Filter `.tasks[]` client-side:

1. `status === "pending"`
2. All IDs in `depends_on[]` must have `status === "done"` — skip if any dependency is not done
3. `requires_human` must not be `true` — skip until cleared

Priority order when multiple tasks are eligible:
1. Lowest `tier` first
2. Highest `priority` first (`critical` > `high` > `medium` > `low`)
3. Lower ID = created earlier

---

## Step 4 — Claim the Task (Lock)

```
PATCH /api/projects/{projectId}/tasks/{taskId}/lock
```

Body:
```json
{
  "agent": "AGENT NAME",
  "reclaim_after_minutes": 15
}
```

Response `200`:
```json
{
  "success": true,
  "taskId": "task-001",
  "task": { "status": "in_progress", "locked_by": "AGENT NAME", ... }
}
```

Error `409` — dependency not met:
```json
{ "error": "Dependencies not satisfied", "message": "Blocked by incomplete dependencies: task-003" }
```

Error `409` — human gate:
```json
{ "error": "Requires human approval", "message": "Task task-001 requires human approval before it can be claimed" }
```

Error `400` — task not claimable (status is `done`, `failed`, or `blocked`).

---

## Step 5 — Send Heartbeats While Working

Send a heartbeat every `heartbeat_interval` seconds (default 30). This extends
the lock by 15 minutes so it is not reclaimed.

```
PATCH /api/projects/{projectId}/tasks/{taskId}/heartbeat
```

Body:
```json
{ "agent": "AGENT NAME" }
```

Response `200`:
```json
{ "success": true, "reclaim_after": "2026-02-25T14:45:00Z" }
```

---

## Step 6 — Complete the Task

```
PATCH /api/projects/{projectId}/tasks/{taskId}
```

Body:
```json
{
  "status": "done",
  "updated_by": "AGENT NAME"
}
```

The server sets `completed` timestamp, clears all lock fields automatically,
updates project metadata counts, and broadcasts a `project:updated` event.

If the task failed:
```json
{
  "status": "failed",
  "updated_by": "AGENT NAME"
}
```

---

## Step 7 — Force Unlock (Recovery Only)

If a task is stuck in `in_progress` and the agent is dead:

```
POST /api/projects/{projectId}/tasks/{taskId}/unlock
```

No body required. Resets status to `pending`, clears all lock fields.

## Status Vocabulary

| Status | Meaning |
|--------|---------|
| `pending` | Available and waiting to be claimed |
| `in_progress` | Locked and actively being worked |
| `done` | Finished successfully |
| `failed` | Execution failed (after retry or unrecoverable error) |
| `blocked` | Cannot proceed — dependency or gate failure |

## Project Status Vocabulary

| Status | Meaning |
|--------|---------|
| `active` | Normal working state |
| `awaiting_approval` | Tier complete, waiting for sign-off |
| `paused` | Workflow halted by user |
| `completed` | Project fully finished |
| `archived` | Moved to `archive/` directory |

## Task Object Schema

```json
{
  "id": "task-001",
  "title": "Scaffold HTML shell",
  "description": "Create index.html with design system tokens",
  "status": "in_progress",
  "priority": "high",
  "tier": 1,
  "agent": "AGENT ARTIST",
  "created": "2026-02-25T10:00:00Z",
  "started": "2026-02-25T10:05:00Z",
  "completed": null,

  "locked_by": "AGENT ARTIST",
  "locked_at": "2026-02-25T10:05:00Z",
  "reclaim_after": "2026-02-25T10:20:00Z",
  "heartbeat_interval": 30,

  "gate": null,
  "depends_on": ["task-001"],
  "requires_human": false,

  "last_updated_by": "AGENT ARTIST",
  "last_updated_at": "2026-02-25T10:05:00Z"
}
```

**Field rules:**
- `id` — string, auto-generated by server as `task-NNN`. Never set by client
- `tier` — integer, never `"1"`, always `1`
- `status` — use exact values from the table above
- `depends_on` — array of task ID strings; empty array `[]` means no dependencies
- `gate` — string gate name (`"qa"`, `"security"`, `"review"`) or `null`
- All timestamps — ISO 8601 with timezone: `"2026-02-25T10:00:00Z"`
- Null fields — must be `null`, never `""` or `"none"` or omitted

## Adding New Tasks

```
POST /api/projects/{projectId}/tasks
```

Body:
```json
{
  "title": "Write auth unit tests",
  "description": "Cover happy path and token expiry edge cases",
  "tier": 3,
  "priority": "high",
  "agent": "AGENT QA",
  "depends_on": ["task-005"],
  "gate": null,
  "requires_human": false
}
```

Server auto-sets: `id`, `status: "pending"`, `created`.
Response `201` returns the created task object.

---

## Updating Other Task Fields

```
PATCH /api/projects/{projectId}/tasks/{taskId}
```

All body fields are optional. Only provided fields are updated.

| Field | Type | Notes |
|-------|------|-------|
| `status` | string | `pending`, `in_progress`, `done`, `failed`, `blocked` |
| `priority` | string | `low`, `medium`, `high`, `critical` |
| `title` | string | |
| `description` | string | |
| `agent` | string | Pass `""` to unassign |
| `depends_on` | string[] | |
| `gate` | string\|null | |
| `requires_human` | boolean | Set to `false` to clear a human gate |
| `heartbeat_interval` | integer | Seconds |
| `updated_by` | string | Sets `last_updated_by` on the task |

`last_updated_at` is always set automatically on every successful PATCH.

## Agent Log Format

Log all work to `agentlogs.md` in the project folder.

```
[AGENT <ROLE>: <TAG>] <TIMESTAMP> | <CONTEXT> | <DESCRIPTION>
```

| Tag | Use |
|-----|-----|
| `STARTED` | Task status changed to `in_progress` |
| `COMPLETED` | Task status changed to `done` |
| `BLOCKED` | Task cannot proceed |
| `DISCOVERED` | New task identified and created |
| `DECISION` | Key choice made |
| `PROGRESS` | Milestone reached |
| `ERROR` | Non-fatal failure |
| `INFO` | General observation |
| `QUERY` | Question for user (non-blocking) |
| `COMMENT` | Note or suggestion |

Log entries must be single lines. Use separate entries for multi-line notes.

Examples:
```
[AGENT ARTIST: STARTED] 2026-02-25T10:05:00Z | task-002 | Beginning HTML scaffold
[AGENT ARTIST: PROGRESS] 2026-02-25T10:15:00Z | task-002 | Design tokens applied, 80% done
[AGENT ARTIST: DISCOVERED] 2026-02-25T10:20:00Z | task-002 | Missing icon set, creating task
[AGENT ARTIST: COMPLETED] 2026-02-25T10:30:00Z | task-002 | index.html scaffolded, CSS vars in place
```

---

## Tier Boundary Protocol

When all tasks in a tier reach `done`, log completion and wait for approval
before starting the next tier.

```
[AGENT QA: COMPLETED] 2026-02-25T15:00:00Z | Tier-1 | All 4 tasks done, gate cleared
[AGENT QA: QUERY] 2026-02-25T15:00:01Z | Tier-1→2 | Ready to proceed. Awaiting approval.
```

Do not start any next-tier tasks until AGENT TASKMASTER confirms the tier is approved.

## Example Workflows

### Standard Task — Coder Agent

```
1.  GET /api/projects/{projectId}
    Filter .tasks for status=pending, tier=2, depends_on all done
    → task-004: "Implement login form validation"

2.  PATCH /api/projects/{projectId}/tasks/task-004/lock
    { "agent": "AGENT CODER", "reclaim_after_minutes": 15 }
    → 200, status now in_progress

3.  Log: [AGENT CODER: STARTED] 2026-02-25T10:00:00Z | task-004 | Beginning form validation

4.  Do the work. Send heartbeat every 25s.

5.  Discover missing test coverage:
    POST /api/projects/{projectId}/tasks
    { "title": "Write validation unit tests", "tier": 3, "priority": "high", "depends_on": ["task-004"] }
    Log: [AGENT CODER: DISCOVERED] 2026-02-25T10:45:00Z | task-004 | Tests missing, created task-009

6.  PATCH /api/projects/{projectId}/tasks/task-004
    { "status": "done", "updated_by": "AGENT CODER" }

7.  Log: [AGENT CODER: COMPLETED] 2026-02-25T11:00:00Z | task-004 | Validation implemented
```

### Failed Task — Retry and Escalate

```
1.  Agent fails mid-task. Task remains in_progress with stale lock.

2.  AGENT TASKMASTER detects reclaim_after has passed:
    Log: [AGENT TASKMASTER: ERROR] ... | task-005 | Lock stale, reclaiming for retry

3.  PATCH /api/projects/{projectId}/tasks/task-005/lock
    { "agent": "AGENT CODER" }
    Re-dispatch agent

4.  If agent fails again:
    PATCH /api/projects/{projectId}/tasks/task-005
    { "status": "failed", "updated_by": "AGENT TASKMASTER" }
    Log: [AGENT TASKMASTER: QUERY] ... | task-005 | Failed twice — escalating to user
```
